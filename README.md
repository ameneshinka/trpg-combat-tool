# 拚點戰鬥系統 — 戰鬥追蹤工具

KP 帶線上跑團時，與玩家共用的**戰鬥狀態追蹤與計算工具**。純靜態、無 build step。

## 規則的真相來源：三個 skill

程式碼**不**內含規則定義。所有規則以 skill 為準（舊的 `拚點戰鬥系統_規格書.md` 已作廢刪除）：

| Skill | 負責 |
|------|------|
| `trpg-clash-rules` | **規則的單一真相來源** —— 拚點、傷害、狀態、回合流程、角卡對應數值 |
| `trpg-combat-webapp` | 怎麼實作 —— 架構決策、資料模型、KP 介面、同步、部署紀律 |
| `trpg-character-design` | 角色設計與平衡分析方法 |

改動任何計算邏輯前，先讀 `trpg-clash-rules`。

## 快速開始

```bash
python dev-server.py 8731
```
開 <http://localhost:8731>。直接開 `index.html`（file://）也能跑單機。

- **單機**：KP 一人操作，完整打完一場。
- **建立房間（KP）／加入房間（玩家）**：需先填 `js/firebase-config.js` 的 `databaseURL`。
  KP 端權威 —— 玩家只送宣告／骰值，KP 採用後才寫入正式狀態。

**回歸測試**：開 <http://localhost:8731/tests/>（283 項，含 skill 指定的兩個驗算）。

## 檔案結構

```
engine/               純計算，無 DOM 依賴、可單元測試
  effects.js          效果鉤子（技能層級 ＋ 逐枚硬幣：使用時／正面時／命中時／命中後／使用後）
  states.js           層數/級數管線、持續狀態、觸發、混亂/恐慌、震顫/瀑
  clash.js            拚點（碎幣模型、綠幣對消、判輸、專注力結算）
  damage.js           傷害（逐枚累加、分組相乘、凝神、防守）
  passives.js         被動「具名函式」註冊表（邏輯寫死在這）
  turn.js             六階段控制器、DEX 定序、攔截、槽位、抽技能
data/
  characters.js       ★ 唯一的「改平衡」檔案：NPC 倉庫、PC 名單、tuning
ui/
  coins.js            擲硬幣動畫（回放引擎的擲幣記錄）
  panels.js           實體面板、結算順序、事件 log
  detail.js           角色詳情浮窗（技能／被動文本、KP 覆寫）
  library.js          NPC 倉庫與本場編成（挑選 → ×N 投放）
  battle.js           推進 turn generator、渲染手動骰與宣告表單
  app.js              設定畫面、連線模式、KP 裁定玩家輸入
js/
  sync.js             Firebase 同步層（SDK 用到才動態載入）
  firebase-config.js  ← 填你的 Firebase 設定
tests/                回歸測試（瀏覽器開啟）
database.rules.json   Firebase 安全規則
```

**調平衡只改 `data/characters.js`**，永遠不用進 `engine/`。
被動邏輯是程式碼（形狀差異太大，資料驅動表達不了跨實體偵測／遞迴／延遲債務），
但**數字一律放在角色的 `tuning`**。

### 四名 PC 與逐枚硬幣效果

四名 PC 的技能幾乎「每一枚硬幣的效果都不同」（威爾技能B 三枚給的震顫級數各異、
旭技能D 四枚各自引爆），所以技能資料用 `coinEffects[]` 逐枚描述，
索引對應 `coins[]` 的**原始位置**（傷害結算會濾掉已損失的硬幣，錯位會掛到錯的硬幣上）。

| 鉤子 | 時機 |
|---|---|
| `skill.onUse` | 技能使用開始、**拚點之前**（威力修正要吃得到拚點）|
| `coin[i].onUse` | 該枚開打前（扣資源、預先施加狀態）|
| `coin[i].onHead` | 該枚正面，且**排在凝神判定之後**（剛上的凝神這枚吃不到）|
| `coin[i].onHit` | 該枚傷害套用後（⚠ **反面照算**，反面只是不加威力）|
| `coin[i].afterHit` | 該枚的 onHit 跑完（震顫爆發等後續）|
| `skill.afterUse` | 整把跑完；設 `runtime.repeat` 可要求重複使用 |

**通則：拚輸 → 一枚 `onUse` 都不跑** → 資源不會被扣掉。

被動用同一份 ctx（`ctx.heal` / `spend` / `apply` / `allies` / `tremorBurst` / `grant`）。
⚠ 引爆震顫一律用 `ctx.tremorBurst()`，直接呼叫 `States.tremorBurst` 不會廣播，
威爾的槍械破甲與援護射擊就不會被觸發。

### NPC 倉庫：本體與實例分兩層

| 層 | 是什麼 | 誰共用 |
|---|---|---|
| **本體（藍圖）** | `NPC_LIBRARY` 裡的一筆：技能組、被動、基礎數值、slotMap | 同款所有實例共用一份 |
| **戰場實例** | `Characters.spawn(id, n)` 生出的第 1 隻／第 2 隻 | 各自獨立 |

同款小怪的每一隻，**HP／臨時HP／專注力／槽位／狀態／印記／資源／宣告全部各算各的**；
共用的只有本體定義 → **調平衡改一筆，全場同步**。
實例 id 一律 `藍圖id#n`，顯示名在兩隻以上時加 A／B／C 後綴。

新增一款 NPC = 在 `NPC_LIBRARY` 加一筆（「哥布林兵」那筆附完整換算註解，可當填表範本）。
**倉庫沒有資料輸入介面**（依 webapp skill）—— 網頁只做「瀏覽 → 選 → ×N 投放」。

⚠ 深拷貝一律用 `Characters.cloneSpec()`，**不要用 `JSON.parse(JSON.stringify())`**：
後者會把技能的 `onUse`／`onHit` 與被動函式靜默吃掉。

## 未定義的裁決（本工具的暫行選擇）

規則 skill 未明訂、實作時必須選一個做法的地方。**要改請直接說**：

1. **【防守】是否需要拚贏才生效？**
   本工具採「**使用即生效**」——不論拚點輸贏都給臨時生命值。
   理由：臨時生命值的用途就是吸收這次傷害；若只在拚贏時生效，而拚贏本來就不會被打中，效果會近乎無用。

2. **無人攻擊時使用【防守】** → 照樣給臨時生命值（視為自我增益）。

3. **玩家端可自行填寫自己角色的手動骰**（1d6／傷害乘數／凝神），KP 端採用。
   `confirmPairing`、`batchTarget` 與 NPC 槽位永遠只有 KP 能操作。

4. **NPC 的技能抽選 1d6 由工具代骰**（骰值照樣寫進事件紀錄）。
   規則對 PC/NPC 一視同仁要求手動輸入，但桌邊放 5 隻小怪就要手擲 10 次 —— 純操作成本，不影響結果。

5. **NPC 菜單附「KP 自由選」逃生門**（無視抽選限制，用了會在 log 留 ⚠ 標記）。
   預設仍照抽 —— 機率結構 A 75%／B 55.6%／C 30.6% 是設計的一部分，
   「這回合抽不到大招」是敵人也要承受的代價。隱藏技（喚出專用）不列入自由選。

6. **【虛弱】不影響防禦型技能** —— 引擎把強壯／虛弱做成「只改攻擊型」，防禦型只吃屏息／遲鈍。
   `states.md` 的表格沒有限定攻擊型，兩者字面有出入。
   理由：結月的防守文本自帶「每 3 層虛弱，幣威 +1」的補償；若虛弱同時削它的基威，
   那個補償是淨虧、毫無意義 —— 所以設計意圖應該是不影響。

7. **【恍惚】在拚點擲幣時也觸發**（依規則書「使用技能擲硬幣時」的字面）。
   ⚠ 觸發粒度是「每枚各一次、每次層 −1」→ 1 層只廢掉 1 枚；
   而拚點比傷害早，所以恍惚通常會在拚點階段就被消耗掉。

8. **旭的被動2／被動4 對敵方的增減改寫為「本回合限定」** —— 照文本字面
   （回合開始給敵人 3 層【傷害弱化】、回合結束再給 3 層【傷害強化】抵銷）淨效果正確，
   但兩邊的層數會無限往上疊（第 10 回合敵人身上掛著 20 層 + 20 層）。
   改成「回合結束移除自己給的那 3 層」，效果等價、面板乾淨。

9. **【迅捷】【綁縛】每層 ±5「點」DEX，不是 ±5%。**
   ⚠ `states.md` 寫的是「DEX ± 層×5%」—— 那是受 COC 角色卡書寫習慣影響的筆誤，
   設計原意是定值加減。**規則書那份需要同步更新。**
   有效 DEX **下限為 1**（再怎麼壓也不會變 0 或負數）；層數上限維持 10。
   後果：定值加減對低 DEX 角色的相對影響大得多
   （和真 50 吃 4 層綁縛 → 30，舊制是 40），女僕的綁縛因此變成真威脅。

10. **攔截的 DEX 比的是「攻擊者」，不是被保護的隊友。**
   ⚠ `lifecycle.md` 原文寫的是「嚴格大於**被攔技能當前目標**」（＝被保護的隊友）。
   本工具改成比攻擊者 —— 攔截的語意是「比對方快，所以橫插得進去」。
   **後果**：慢角色幾乎攔不到人。以女僕（DEX 65）為例，全隊只有旭（90）攔得到；
   威爾（65，相等不行）、結月（60）、和真（50）都不行。要改回來只是一行。

11. **攔截照宣告綁定** —— 指名攻擊者就只攔他；他本回合沒攻擊該名隊友時，才退回
   「攔任何打他的人」。指名了卻因 DEX 不足被拒 ＝ 攔截失敗，不會默默改攔別人。

   宣告表單只列出**真的攔得到**的攻擊者（`Turn.interceptableAttackers`，判斷條件與
   `buildPairing` 同源、由測試釘住）。一個都攔不到時連「攔截」這個動作都不會出現，
   並顯示原因 —— 不讓人選到必定被打回票的對象、白費一個槽位。

12. **和真被動1「偵查獲得獎勵骰」不實作** —— 那是 COC 的技能檢定，不在拚點系統內，只顯示文本。

## 擲硬幣動畫

硬幣是**程式自動擲**的，而且一整場拚點是在 generator 的**同一步**裡同步跑完
（`resolveClash` 中間不 yield）—— UI 沒辦法插在中間演。
所以 `engine/clash.js` 有一個**預設關閉**的擲幣記錄器，`ui/coins.js` 負責回放：

```
advance() → Clash.startRecording() → iter.next() → Clash.stopRecording()
          → Coins.play(groups)（await）→ 才顯示下一個提示
```

⚠ 記錄器沒開時完全不收集，引擎行為與沒有這層時一模一樣（有測試釘住）。

- 一組擲幣一段動畫：拚點的一次交換 = 雙方硬幣並排、贏方高亮
- 右上角「跳過」跳過當下這一串；標題列的「擲幣動畫」開關可整場關掉
- 節奏常數在 `ui/coins.js` 頂端（翻轉 500ms／停留 450ms／組間 120ms）
- 只在 KP／單機端播，玩家端不同步

| 硬幣 | 正面 | 反面 |
|---|---|---|
| 普通 | `#F7D443` | `#9c7310` |
| 紅 | `#FF2400` | `#7B1818` |
| 綠 | `#3FCF6B` | `#1F6B39` |
| 碎幣 | 同紅幣 ＋ 虛線框 ＋ 裂痕 ＋「+1」（有效幣威已變成 1）| 同上 |

**硬幣上顯示的是擲出的 1d100 數字**（COC 式），旁邊標「門檻 62（擲 ≤62 為正面）」。
門檻 = 50 + 專注力，恆為 10~90 的整數 → 「擲 ≤ 門檻」與 `Math.random() < 機率`
**機率完全相同、不是近似**。這是給玩家自己驗算用的 —— 連續看到反面時不必懷疑系統。
事件紀錄只寫摘要（`門檻 62｜擲 43、82、37 → 正面 2／3`），不逐枚膨脹。

## 已知限制

- **不使用 localStorage／sessionStorage**（依 webapp skill）。
  → 重整後 clientId 會變：玩家需重選角色；KP 的狀態從 Firebase `/state` 還原。
- Firebase 設定金鑰會公開在前端（正常），**但安全規則必須發布**（見 `database.rules.json`）。
- 執行期**不呼叫任何 LLM** —— 戰鬥計算是確定性運算，必須每次一致。

## 部署紀律（webapp skill）

- 平衡測試在本機跑，不用每次都部署。
- 跑團**前一天**定版、部署、自己完整測一場。
- **帶團當天不動程式碼**。桌邊要調就用 KP 面板的數值覆寫（只改數字、不改邏輯），事後再回頭改 `characters.js`。
